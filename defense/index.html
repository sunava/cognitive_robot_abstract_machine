// 02 · motivation — "prepare breakfast"

Easy to state. Hard to execute.

cut(bread, into=slices)
pour(juice, into=glass)
spread(butter, onto=toast)
mix(ingredients, in=bowl)
# none of these is executable as stated

Each requires physical contact with an object that will be permanently changed.

What the description leaves open:

  • Tool — which knife, whisk, container?
  • Contact site — where on the object may contact begin?
  • Motion form — sawing or slicing? tilting or shaking?
  • Force limits — how hard before the object breaks?
  • Stopping condition — when is the action done?

All five depend on the specific geometry and material of the object at hand.

// 03 · the problem — underdetermination

State-changing manipulation is a representational problem

  • Transport changes an object's pose. State-changing manipulation changes its material, containment, distribution, or surface state — and the change is irreversible.
  • Once the knife has entered the bread at the wrong position, no subsequent action restores the original object → correctness must be checked before contact and maintained during it.
  • Correctness lives in relations between tool, object, scene, and material — an action name or a fixed trajectory loses exactly these conditions.

Same command, different physics:

cut(x)  cucumber ✓ — but butter smears: comparable surfaces, different material response
pour(x)  water ✓ — but honey needs a different tilt profile; frozen contents none at all
cut(x)  the cherry pit is invisible to the bounding box — geometry alone can't place the cut

// 04 · research question & hypotheses

How can manipulation actions be represented so that they can be correctly executed within a defined task scope — across varying object instances, tools, robots, and environments — while satisfying the relevant constraints?

H1
Small, finite coverage. Within a defined task scope, the instances of a manipulation action category can be described by a small number of action templates plus specialisations and parameterisations — parameters left unbound.
structure
H2
Constraints as first-class structure. A template can be a constraint-aware, constraint-enforcing symbolic structure describing a set of admissible executions — applicability conditions, motion bounds, success criteria explicit at each phase.
constraints
H3
Contextual knowledge is necessary. Material properties, object structure, and tool affordances resolve execution-critical distinctions that geometry alone cannot. Null model H0,3: object geometry alone suffices.
knowledge

Operationalised as seven requirements R1–R7: structural transfer · object-relative grounding · explicit constraints · runtime instantiation · monitored execution · diagnosable failure · implementation usability.

// 05 · approach

Separate the stable action structure from its runtime bindings

The stable part is the phase sequence with its constraints. The variable part — object slots, scene bindings, material-dependent parameters — is grounded at runtime. A new object requires new geometric anchor points, not a new template.

// 06 · system architecture — the CRAM cognitive architecture as execution substrate

Five components, one contract

PyCRAM
Plan executive. Plans as trees of control-flow nodes; designators as runtime records of partial commitments; ORM-backed execution log. (Dech & Hassouna, 2024)
RoboKudo
Perception as queries — task-specific Perception Pipeline Trees supply the evidence that resolves object references, anchored in the digital twin.
Semantic Digital Twin
The shared world model: stable object identities + geometric layer for grounding and collision-aware execution, synchronised with physics simulation (Multiverse).
KnowRob
Knowledge & reasoning: SOMA dispositions (cuttable, pourable, …), Entity Query Language, Ripple Down Rules. Determines admissibility, not trajectories.
Giskard
Constraint-based motion control — solves a quadratic program per control cycle over the grounded constraints; absorbs disturbances without task-level replanning.
constraints, not trajectories
"Blade within 3 mm of the separating surface, contact force 5–20 N, blade normal within 10° of the surface normal — any trajectory satisfying this is a valid cut."

Grounding in image-schema theory: cutting = Contact + separation event · pouring = Containment → Source-Path-Goal boundary crossing · mixing = circulation inside Containment · wiping = Contact on Support. First systematic mapping from Hedblom's ISLFOL to continuous trajectory invariants for household action.

// 08 · four primitive families — one invariant each

Each family is defined by a physical invariant

separation & division
d(t) monotone ↑  ∧  q(t)·n = 0
A separating manifold is crossed: monotone penetration along the surface normal; sawing adds tangential oscillation q(t) = A·sin(ωt)û. Techniques: slicing, sawing, julienne.
aggregation & mixing
c(p(t)) > 0  ∀t
Motion stays confined to the container interior — c is the signed clearance function. Circular, elliptical, orbital are path shapes of the same generator.
material transfer
f(t) ≥ 0,  ḟ(t) ≥ 0
Material crosses the container boundary, forward only. Tilting, tapping, shaking differ solely in the temporal profile of f(t), not in the invariant.
surface interaction
qshear·n = 0  ∧  Fn > 0
Motion stays in the tangent plane of a contact surface while contact force is maintained. Wiping removes material; spreading distributes it — same generator, different material direction.

No claim that all manipulation verbs reduce to four families — this is the evaluated scope. The structure extended cleanly to bottle-opening in supervised follow-up work.

Object-Anchored Action Template (OAAT)

# OAAT instance
OA = (TA, GA, kA, SA, CA)
  phases · geometry type · primitive family ·
  open slots · applicability + motion bounds
  • Phases Φᵢ = (family, anchor, params, interval, pre, post, success) — each phase's postcondition feeds the next's precondition; the success criterion measures the material effect, not motion completion.
  • Action-relative geometry — the template expects a type of geometry (separating surface, bounded interior, opening, contact surface); bread and cucumber differ in values, not in type.
  • Applicability constraints checked before irreversible contact: cuttable ← compliance > cmin ∧ hasSeparatingSurface · pourable ← flowable(contents) ∧ hasOpening · mixable · wipeable / spreadable.
  • Executable iff every required slot is bound: S_T ⊆ dom(B_g).

Why geometry alone fails (H0,3): for a cherry, geometry offers one wide admissible anchor zone; the knowledge query hasPart(pit) removes the pit axis, leaving two admissible bands. Geometry proposes — knowledge disposes.

// 11 · monitored execution — violations are named events

Three recovery scopes, one untouched template

①
Controller correction — phase and bindings preserved. Small contact-force variation; bowl drift within the admissible volume. Giskard absorbs it.
local
②
Local re-binding — phase preserved, slots recomputed. Object displaced on its support → new anchor, same action identity.
re-bind
③
Full replanning — failure no longer local: object is no longer the intended target, support lost, residue elsewhere.
re-plan

Example — pouring failure taxonomy:

  • NoFlowDetected → semantic replanning (empty source, occluded opening)
  • LateFlow → additional tilt, slower continuation
  • FlowInterrupted → oscillatory recovery, reparameterisation
  • ContactDetected → safety transition
  • PourSuccess — confirmed only from sustained-transfer evidence, never from tilt completion alone

Critical segments = the execution-side view of phase invariants that must hold with high precision (blade on surface, flow over opening) — not a separate representation layer.

// 17 · failure analysis — read the statistics carefully

The recovery paradox

A naive reading: "recovery reduces success." Wrong — recovery fires after a collision failure, so the recovery group is pre-selected for the hardest contexts. A high recovery rate signals resilience, not brittleness.

Failure modes localise to embodiment, never to the template:

  • Stretch: 180 of 182 failures (98.9%) are motion stalls in all three environments → structural arm–primitive mismatch, not obstacle avoidance.
  • Rollin' Justin: 34 of 43 failures (79.1%) hard controller failures, concentrated in the kitchen.
  • ARMAR-7: 123 stalls + 11 hard failures at joint limits; its recovery motion succeeds in only 10.2% of attempts.
  • Across all 1,915 runs: no failure originates in the OAAT phase structure itself.

// 20 · contributions

What this thesis puts on the table

  • Representational: the OAAT — phase structures anchored in action-relative object geometry, applicability as explicit material constraints.
  • Empirical: the phase structure of household manipulation is stable and derivable from observation alone.
  • Grounding: layered query + policy resolution turns underspecified designators into executable motion; the geometry-only null model demonstrably fails.
  • Evaluation: one representation, eight morphologically diverse robots, three environments — 7,693 executions, zero template rewrites.
  • Real-world: RoboCup@Home deployment; PR2 cutting + 94.2% pouring with perception in the loop.
  • Open science: NEEM execution logs in the EASE dataset · PyCRAM (co-author) with 95% test coverage · code on GitHub, branch thesis.
  • Virtual Research Building: the experiments live on as the Action Cores Lab — replay, reconfigure, and re-run every execution in the browser (vrb.ease-crc.org).
  • 9 publications — IJCAI, Frontiers in Robotics & AI, K-CAP, ICRA40, Social Robotics.
